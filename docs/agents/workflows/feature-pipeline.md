# Workflow: feature-pipeline

Вход: путь к заполненному RFC и явные пользовательские ограничения. Выполняет Orchestrator по [ролевому протоколу](../roles/orchestrator.md), [общему протоколу](../protocol.md) и [AGENTS.md](../../../AGENTS.md). Этот файл не задаёт отдельную версию архитектурных правил.

## Запуск

1. Зафиксируйте base commit и `git status`; чужие изменения не включайте в diff задачи.
2. Проверьте ровно пять основных блоков RFC и достаточность критериев. При недостаточности — `RFC_REQUIRED`/`BLOCKED`, без Research.
3. Переведите состояние в `RESEARCHING`; вызовите Researcher с Task Packet и критериями. Получите Research Report с проверяемыми ссылками.
4. Разбейте реализацию на атомарные задачи по пяти зонам и постройте порядок зависимостей. Нужность `cmd/` или `internal/config/` — отдельный integration blocker.
5. Последовательно вызывайте Coder: один критерий, одна зона, owned files, один zone skill, актуальная база и предыдущие артефакты.
6. После каждого вызова проверяйте `git status` и diff: разрешены только owned files. Отклоните выход за зону через цикл исправления или `BLOCKED`; не скрывайте его.
7. Передайте Reviewer RFC, Research, полный актуальный diff, файлы и прошлые замечания.
8. При `CHANGES_REQUESTED` верните конкретные findings соответствующему Coder. После исправления повторите Reviewer; максимум три непродуктивных цикла одной проблемы.
9. После `HANDOFF` Reviewer вызовите Tester с актуальным diff и требуемым окружением. Обязательны базовые проверки и применимые сценарии RFC.
10. При `FAIL` верните доказательства Coder и повторите необходимые Reviewer/Tester. Не игнорируйте `SKIPPED`.
11. Верните `READY_FOR_HUMAN` только после чистого ревью и честно зафиксированных проверок, иначе `BLOCKED`. В итоге перечислите файлы, findings, команды, exit codes, непроверенные области и риски.

Никакой этап не выполняет автоматический commit, push, merge или публикацию PR. Финальное решение принимает человек.
