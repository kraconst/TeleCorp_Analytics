# RFC: Синхронизация личных диалогов Telegram

- **Статус**: Implemented (1A, 1B)
- **Дата**: 26 ноября 2026 года
- **Ответственные**: Группа 1, очередь реализации 1A
- **Файлы 1A**: `internal/config/{config,telegram_test}.go`, `internal/usecase/{interfaces,chat_test,review_iteration3_test}.go`, `internal/storage/postgres/{account,account_telegram_test}.go`, `internal/telegram/{client,sync_client,sync_reader,account_session,sync_client_test,account_session_test}.go` и этот RFC.

## 1. Фича

Система использует сохранённое подключение рабочего аккаунта для чтения личных диалогов и новых сообщений. Оператор может настроить прокси для подключений к Telegram.

## 2. Бизнес-требования

- Чтение выполняется от имени рабочего аккаунта своей компании, который был авторизован ранее. Синхронизация включает личные диалоги с другими пользователями, исключая ботов, группы, каналы и удалённых пользователей.
- Для существующего чата история начинается после последнего сохранённого Telegram ID. Каждая выгрузка возвращает сообщения от старых к новым. При неудаче чтения истории вызывающий код получает ошибку без частичной выборки.
- Отозванная, просроченная или отсутствующая Telegram-сессия переводит аккаунт в `disconnected`, подтверждённая блокировка — в `banned`. Сетевые сбои, отмена, ошибки БД и ошибки доступа к ключу шифрования сохраняют текущий статус.
- 1A передаёт данные через внутренний интерфейс. Приёмка включает многостраничное чтение, сохранение сессии в пределах аккаунта и компании, безопасное повторное использование сессии, отмену ожидания `FLOOD_WAIT`, сохранение CLI и возможность запустить приложение без настроек Telegram.
- 1B сохраняет сообщения и дневные счётчики, поддерживает ручной и периодический запуск. Один аккаунт обрабатывается одним запуском в процессе. Ошибка аккаунта не мешает воркеру перейти к следующему. Повторное чтение не увеличивает счётчики повторно.
- Оператор импортирует ранее авторизованную файловую сессию через локальную команду. Она сверяет профиль Telegram с аккаунтом компании. AI-обработка относится к Группе 2 и может подписаться на уведомление об изменении чата.

## 3. Технические требования

- Выполнить зоны usecase (контракты), PostgreSQL (состояние аккаунта) и integrations (MTProto). Для 1A описание задачи отдельно назначает `internal/config/config.go`. Используются текущие зависимости, миграции, Docker и интерфейс CLI.
- Секция `TelegramConfig` читает `TELEGRAM_API_ID`, `TELEGRAM_API_HASH`, `TELEGRAM_PROXY`, `USE_PROXY`, `TELEGRAM_NO_PROXY`, `TELEGRAM_SYNC_ENABLED`, `TELEGRAM_SYNC_INTERVAL` и `TELEGRAM_SYNC_BATCH_LIMIT`. Интервал по умолчанию 60 секунд, размер страницы 100 (допустимы 1–100), фоновый запуск по умолчанию выключен. Клиент требует пару API ID/hash и `TELEGRAM_SESSION_KEY` (32 случайных байта в стандартном Base64) для серверных сессий. При отсутствии настроек `config.Must()` продолжает работать. Включение воркера и ответ `503` при недоступной интеграции применяет 1B.
- Серверный `session.Storage` шифрует данные gotd через AES-256-GCM со случайным nonce, версией формата и привязкой к паре `company_id`/`id`. Получение или изменение сессии и запись нового статуса используют оба идентификатора в SQL. Ключ, данные сессии и реквизиты прокси не публикуются. Утилита разработки сохраняет файловую сессию своим текущим путём.
- На каждый RPC отводится до 15 секунд. Для всей операции без дедлайна вызывающего кода используется лимит 10 минут. `FLOOD_WAIT` повторяет RPC после указанной задержки с учётом контекста. Невозможность продолжить пагинацию приводит к явной ошибке. Закреплённые диалоги читаются отдельно в основных чатах и архиве. Остальные диалоги используют `OffsetDate`/`OffsetID`/`OffsetPeer` последнего диалога из исходной страницы, включая отфильтрованных собеседников. `MessagesGetHistory` передаёт `MinID` и продвигает `OffsetID` по полученным Telegram ID. Вложения определяются по метаданным.
- Запись сессии и статуса — отдельные атомарные операции. Последняя активность обновляется монотонно. 1B сериализует запуски на аккаунт и ведёт курсор только после записи сообщения. Отсутствующий аккаунт возвращает `ErrNotFound`, невалидные параметры — `ErrValidation`, остальные сбои сохраняются в цепочке ошибок.
- 1B меняет usecase, PostgreSQL, HTTP и точку сборки `cmd/app`. Транзакция на диалог сохраняет контакт, чат, новые сообщения, метаданные и дневные счётчики вместе. Сетевые запросы выполняются вне транзакции. Прогресс считается только по зафиксированным транзакциям. `awaiting_reply_since` хранит начало серии входящих после последнего исходящего. Даты статистики берутся в часовом поясе компании.
- Ручной запуск и воркер используют один экземпляр `SyncUsecase`. Повторный запуск того же аккаунта из этого процесса получает конфликт. При развёртывании с несколькими репликами одному аккаунту нужен внешний координатор запусков. Воркер отменяется вместе с HTTP-запросами при остановке сервера.
- Опциональный `OnChatUpdated(ctx, companyID, chatID)` получает только события зафиксированных транзакций с новыми сообщениями. Очередь ограничена, переполнение отражается в статистике. Обработчик уведомлений работает на контексте приложения.
- Проверки включают форматирование, `go vet ./...`, `go test -race ./...`, `go build ./...`, моки Telegram RPC и изолированные проверки хранилища. Для настоящей проверки PostgreSQL нужен специально назначенный тестовый сервер. Для работы с реальным Telegram отдельно нужна авторизованная рабочая сессия.

## 4. Контракты

- `POST /accounts/:id/sync` принимает положительный ID аккаунта и `?company_id=`. По соглашению существующего API отсутствие `company_id` означает `1`. Это область данных, выбранная вызывающим, до появления полноценной аутентификации. Тело запроса не требуется. Ответ `200` содержит `chats_processed` и `new_messages` и, при переполнении очереди, `notifications_dropped`. `400` означает невалидный ID, `404` — аккаунт вне области запроса, `409` — конфликт запуска, неактивный аккаунт или требуется переподключение. Без настроенного клиента возвращается `503`. Другие ошибки возвращают `500` и, при частичном импорте, уже сохранённые счётчики.
- `go run ./cmd/app import-telegram-session <company-id> <account-id> <session-file>` импортирует сессию, созданную CLI, при наличии `TELEGRAM_API_ID`, `TELEGRAM_API_HASH` и `TELEGRAM_SESSION_KEY`. Аккаунт должен существовать в компании. Команда проверяет профиль Telegram по сохранённому ID, если он уже известен, и номеру аккаунта. После проверки сессия сохраняется зашифрованной, `telegram_user_id` заполняется, статус становится `active`. Импорт для уже активного аккаунта выполняется при остановленных синхронизациях этого аккаунта.

- `TelegramSyncClient.WithAccount(ctx, companyID, accountID, fn)` открывает авторизованное подключение для указанного аккаунта. Переданный в `fn` обработчик чтения действует только в пределах вызова и принимает переданный контекст. При подключении нового аккаунта 1B проверяет соответствие его Telegram-профиля рабочему аккаунту до первой записи через `NewAccountSessionStorage`.
- `ListDialogs(ctx)` возвращает ID собеседника, имя, username и число непрочитанных сообщений. Данные для авторизации на стороне Telegram остаются внутри подключения. После `ListDialogs` метод `ListHistory(ctx, dialog, afterID)` читает сообщения строго после указанного ID. `domain.Message` содержит Telegram ID, направление `in`/`out`, текст, время UTC и тип `photo`/`document`/`voice` при наличии. Внутренний `ChatID` заполняет 1B. Пустые выборки возвращают пустые срезы.
- `TelegramAccountStateRepository` предоставляет `LoadSession`, `UpdateSession`, `UpdateLastActivity` и `UpdateSessionStatus`. Все операции требуют `companyID` и `accountID`. Пустая сессия возвращает `session.ErrNotFound` на уровне адаптера gotd. Ошибка сессии возвращается вызывающему коду даже при успешном сохранении нового статуса.

## 5. Схема БД

1A переиспользует `accounts.id`, `accounts.company_id`, `accounts.session` (`BYTEA`, допускает `NULL`), `accounts.status` и `accounts.last_activity_at`. PK и связь с `companies` сохраняются. `contacts`, `chats`, `messages` и `account_daily_stats` будут записываться слоем 1B.

Новая миграция, индексы и перенос данных для 1A не требуются. У существующих аккаунтов без сессии сохраняется возможность пройти авторизацию. Файловая сессия CLI или данные неизвестного формата требуют отдельного явного импорта или повторного подключения.
